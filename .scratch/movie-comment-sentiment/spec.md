# Spec: 基于方面级情感分析的电影评论分析系统设计与实现

> Feature slug: `movie-comment-sentiment`
> Status: ready-for-agent
> 来源：5 轮 grilling 的决策记录（`docs/决策记录.md`）+ 两轮子代理研究结论（`docs/决策记录.md` §9）
> 关键决策：不训练模型，仅部署现成模型 + 预留训练管线；单人 8–10 周有效开发量。

---

## Problem Statement

一个想看一部电影的影迷，面对的是一大片真假难辨的短评：有人刷好评，有人只骂"剧情拖沓"却对演技只字不提。他真正想知道的不是"平均几颗星"，而是——**这部电影的剧情、演技、画面、音乐、节奏，各自到底怎么样？**

现有的影评平台只给一个总体分数，或者一堆没有重点的好评差评列表。影迷要自己一条条读，才能拼出一部电影的多维口碑。这既费时，又因为评论极性两极分化（5 星和 1 星占多数）而难以判断真实的中间地带。

而现有的中文影评情感分析方案，要么是纯规则（关键词匹配，误判率高），要么是调用 Python 模型（部署复杂、离线不可用），要么只给一个"正面 78%"的总分——**没有人告诉影迷"演技很好但节奏拖沓"**。

## Solution

一个 **Spring Boot + Vue 3** 的电影评论智能情感分析系统。影迷搜一部电影，看到的不是"4.2 分"，而是一张**方面雷达图**：剧情、演技、画面特效、配乐音效、节奏、台词六个维度各自打分，并附带**好评/差评代表句（带置信度和触发关键词）**，让他一眼看出"这片子好在哪、差在哪"。

影迷也可以提交自己的评论，**实时**获得情感分析结果（含置信度和触发词），并可在 **L0 规则引擎 / L2 本地深度模型 / L1 大模型**三种方案间切换对比——系统是"活"的，不是录屏。

对答辩老师来说，这套系统的价值在于：它把**方面级细粒度情感分析**（自建五维评价体系）、**纯 Java ONNX 本地推理**（推理期零 Python）、**可解释性输出**（置信度 + 触发词）、**多模型对比评测**四件事做成了一个能跑、能演示、能量化对比的完整系统。

## User Stories

### 影迷（未登录）

1. 作为一个影迷，我想在首页看到一部电影的海报墙，并按好评率排序，以便快速找到值得看的电影。
2. 作为一个影迷，我想按电影名、演员、导演或关键词搜索电影，以便找到特定影片。
3. 作为一个影迷，我想点进一部电影的详情页，看到情感分布饼图（正面/中性/负面占比），以便了解口碑的总体走向。
4. 作为一个影迷，我想看到这部电影的**方面雷达图**（剧情/演技/画面特效/配乐音效/节奏/台词），以便一眼看清它的好坏维度。
5. 作为一个影迷，我想在雷达图的每个维度旁看到**样本量**（有多少条评论提到了这个维度），以便判断这个分数可信不可信。
6. 作为一个影迷，我想看到这部电影的关键词词云，以便快速了解观众在讨论什么。
7. 作为一个影迷，我想看到好评和差评的**代表句**，每句都标注**置信度**和**触发关键词**，以便了解具体是什么让人觉得好/差。
8. 作为一个影迷，我想看到"这个雷达图分数是基于 N 条提及、正面占比 X%、经贝叶斯平滑后得出"的说明，以便理解分数是怎么算的。
9. 作为一个影迷，我想在电影详情页看到这部电影的评论时间趋势（如果有足够数据），以便了解口碑随时间的变化。
10. 作为一个影迷，我想在电影详情页看到多部相似/相关电影的横向对比柱状图，以便做观影决策。

### 影迷（已登录）

11. 作为一个已登录的影迷，我想提交自己的影评并**立即**获得情感分析结果，以便知道自己的评论被如何理解。
12. 作为一个已登录的影迷，我想在提交评论后看到"这句里触发了'演技在线'这个词，所以演技维度判为正面"的解释，以便理解系统是怎么想的。
13. 作为一个已登录的影迷，我想在提交评论后**稍后**看到大模型（L1）的补充结果（观点抽取、可能的摘要），以便获得更丰富的分析。
14. 作为一个已登录的影迷，我想收藏感兴趣的电影，以便下次直接查看。
15. 作为一个已登录的影迷，我想看到自己提交过的评论及其分析结果的历史，以便回看。
16. 作为一个已登录的影迷，我想切换提交评论时使用的分析方案（L0/L1/L2），以便对比不同方案的结果差异。

### 管理员

17. 作为一个管理员，我想登录后台管理界面，以便进行数据和模型的运维。
18. 作为一个管理员，我想看到数据总览（评论总量、电影数、分析结果数、模型效果对比图），以便了解系统运行状态。
19. 作为一个管理员，我想增删改查电影信息（片名、导演、演员、海报 URL、年份、简介），以便维护片库。
20. 作为一个管理员，我想查看、筛选、删除、导出评论数据，以便清洗脏数据和做离线分析。
21. 作为一个管理员，我想配置爬虫任务（目标站点、电影 ID、抓取数量、延迟间隔），以便补充新数据。
22. 作为一个管理员，我想手动触发爬虫任务，并查看进度和日志，以便监控采集过程。
23. 作为一个管理员，我想在爬虫失败时看到失败原因，且不影响已有数据和系统其他功能，以便演示不翻车。
24. 作为一个管理员，我想**一键重跑全库**的评论分析，以便切换模型后能重新计算所有结果。
25. 作为一个管理员，我想查看每条评论的分析结果（含原始 JSON 快照），以便核对和排查。
26. 作为一个管理员，我想上传、启用、切换 ONNX 模型文件，并记录模型版本，以便管理多个模型版本。
27. 作为一个管理员，我想查看各分析方案（L0/L1/L2）在同一测试集上的准确率、F1、耗时对比，以便产出论文实验数据。
28. 作为一个管理员，我想管理用户账号（禁用/启用、重置密码），以便控制系统访问。
29. 作为一个管理员，我想查看中性阈值 θ 在不同取值下的 F1 曲线，以便为论文的阈值敏感性分析提供数据。
30. 作为一个管理员，我想导出评测报告（含混淆矩阵、per-aspect P/R/F1、Cohen's κ），以便直接引用进论文。

### 系统（隐式需求）

31. 作为一个系统，我想在分析结果缓存命中时不重复调用大模型，以便省钱和加快响应。
32. 作为一个系统，我想在大模型调用超时（3 秒）时降级为只返回本地模型结果，以便请求永不卡死。
33. 作为一个系统，我想把每次分析的完整输出（含置信度、触发词、模型版本）保存为 JSON 快照，以便答辩时证明结果不是编的。
34. 作为一个系统，我想在方面维度样本量不足（< 10 条）时将该维度置灰，以便不显示不可信的分数。
35. 作为一个系统，我想在演示模式下完全不依赖实时网络请求，以便答辩现场不因断网而崩盘。

## Implementation Decisions

### 技术栈（已定稿）

- **后端**：Java 17 (LTS，必须用 **Temurin 17 或 Zulu 17**，其他 JDK 会因 ONNX Runtime 的 Windows 原生库冲突抛 `UnsatisfiedLinkError`) + Spring Boot 3.2.x + MyBatis-Plus + MySQL 8 + Maven。
- **前端**：Vue 3 + Element Plus + ECharts。不采用 Vue 2（已于 2023-12-31 EOL）。
- **AI 推理**：ONNX Runtime Java `1.31.0` + DJL `ai.djl.huggingface:tokenizers` `0.38.0`。共约 69 MB jar。**推理期零 Python。**
- **中文预处理**：HanLP 1.x **`com.hankcs:hanlp:portable-1.8.6`**（注意版本号必须写 `portable-1.8.6`，写 `1.8.6` 会编译失败）。用于分词、词性标注、命名实体识别。
- **缓存**：Redis，只做两件事：① 分析结果缓存（文本哈希 → 结果）② 爬虫任务状态存储。不做会话/限流。
- **LLM**：阿里百炼 DashScope Java SDK `com.alibaba:dashscope-sdk-java:2.23.2`（唯一有官方 Java SDK 的供应商）。同时支持 OpenAI 兼容接口以便切换到 DeepSeek。
- **部署**：Docker Compose（MySQL + 后端 + Nginx 前端）。本地开发 MySQL 用 Docker 跑、后端 IDE 直跑。

### 架构决策

- **单仓库多目录**：`backend/`、`frontend/`、`ml/`、`docs/`、`data/`。
- **三层混合情感分析**，全部实现为 `SentimentAnalyzer` 接口的三个实现类：
  - **L0 规则引擎**：情感词典 + 否定词 + 程度副词 + 自建影视领域词典。论文对比基线。
  - **L2 本地深度模型**：ONNX Runtime 加载 `IDEA-CCNL/Erlangshen-Roberta-110M-Sentiment`（apache-2.0）→ ONNX → int8 量化（约 100 MB）。主推理路径。
  - **L1 大模型 API**：调用 DashScope/DeepSeek，做观点抽取与兜底。
- **实时分析链路**：同步返回 L0/L2 本地结果 + **异步补 L1 大模型结果**。前端**轮询**（500ms 间隔，拿到即停）。L1 调用必须加 **3 秒超时 + 失败降级**。
- **三分类派生方法**（创新点）：L2 输出正/负概率，当 `|p_pos − p_neg| < θ` 判为**中性**；叠加规则信号（评论过短、无情感词、含"还行/一般/凑合"等中性标记词）作为辅助判据。θ 通过验证集网格搜索（0.05–0.50，步长 0.05）确定，并输出 **θ 敏感性曲线**。
- **方面级情感分析**（创新点）：
  - **必须在转折连词处切分子句**（但是/不过/然而/却）——"画面很美但是剧情很烂"不分句会给两个方面同一极性。
  - 方面锚定 + 子句级分类（复用 L2 模型）为主；关键词窗口 + 词典打分兜底；LLM 输出五维情感作对照臂。
  - **只在锚点显式出现时才报告该方面**——接受低召回、保住高精度。
  - 聚合到雷达图分数用**贝叶斯平滑**（小样本向 50 分收缩），同时显示样本量；样本量 < 10 的维度置灰。
  - 六维词表：剧情、演技、画面特效、配乐音效、节奏、台词；雷达图画五轴，第六维单列。**先做覆盖率统计**，覆盖率 < 5% 的维度换掉。
- **可解释性输出**：每个分析结果都带置信度 + 触发关键词。

### 预留训练管线（L3）

- `SentimentAnalyzer` 接口 + `ml/` 目录下完整训练脚本（数据下载→清洗→训练→导出 ONNX，**可跑但暂不启用**）+ 完整评测框架。
- 架构须保证将来训练出的模型**零改动接入**（换 `.onnx` 文件即可）。
- **诚实红线**：脚本若从未跑通，不得在答辩中声称已训练。宁可只展示"管线已就绪"。

### 数据库（关键取舍）

- 方面级分数用**纵表** `comment_aspect`（comment_id, aspect_name, sentiment, confidence），不用宽表——因为维度集合可能调整，纵表零迁移成本。
- `comment_analysis` 表加 `raw_json` 快照列，保存每次分析的完整输出（含置信度、触发词、模型版本）。
- 演示库目标：**20 部电影 × 200 条 ≈ 4000 条**。爬完立即导出 CSV/JSON 存入 `data/` 并提交 Git。

### 数据合规（必须写进论文）

- 豆瓣 `/j/` 接口被 robots.txt **明确禁止**（Disallow `/j/`），抓取属于**有据可查的 ToS 违反，不是灰色地带**。
- 主语料优先使用 `Leoooooops/douban_movie_comments`（**apache-2.0**，唯一有真实许可证的豆瓣数据集）。
- 少量自采用于演示时，**必须在论文中如实披露**违反 robots.txt 的事实。PIPL 适用于含用户名的公开评论；非商业论文、匿名化、不再分发的情况下实际风险低，但 robots.txt 违反是真实暴露点。
- **不得假装合规**。

### 创新点定位（论文主张）

1. **⭐ 纯 Java 通过 ONNX Runtime 部署微调中文 Transformer，推理期零 Python**（已验证空白：GitHub 多种措辞搜索，0 结果）。可量化：约 69 MB jar vs 数 GB Python+PyTorch 镜像。
2. **⭐ 方面级细粒度情感分析**：自建中文电影五维/六维评价体系 + 自建标注集（不存在中文电影 ABSA 数据集）。
3. **⭐ 二分类→三分类派生方法** + θ 敏感性分析。
4. **⭐ 中文电影领域情感词典构建**（通用词典 + 影视领域词扩充）。
5. LLM vs 本地模型的成本/精度对比（实验方法，不单独声称创新）。

### 论文红线（不得违反）

- 不得把文档级准确率当作 ABSA 准确率。
- 不得声称关键词锚定"达到"了它没有的召回率。
- 不得引用未运行的 SOTA 对比或未核实的 F1 数值（研究未能核实任何 ABSA SOTA F1）。
- 不得把 LLM 标注集当作 gold standard。
- 论文必须诚实说明：未自行训练模型、评测仅在公开测试集 + 自建标注集上进行。

## Testing Decisions

### 什么是好测试

只测**外部行为**，不测实现细节。即：给 `SentimentAnalyzer.analyze(text)` 一个中文影评字符串，断言返回的 `AnalysisResult` 里的字段值（情感极性、置信度区间、触发关键词包含某词、方面维度分数）。**不测**内部是走了 L0 词典还是 L2 模型的分支、不测 Spring MVC 层、不测 MyBatis 层、不测 Vue 组件。

### 测试接缝（唯一一个）

**`SentimentAnalyzer` 接口的 `analyze(text) → AnalysisResult`**。

三个实现类（L0/L2/L1）共用同一套测试。评测框架是这个接缝的批量模式，不算第二个接缝。

### 要测的模块

1. **L0 规则引擎**：否定词处理（"不好"→负面）、程度副词加权（"非常好看"比"好看"分高）、影视领域词典命中（"演技在线"→演技正面）。
2. **L2 ONNX 模型**：二分类输出正确性、int8 量化后精度不明显下降、CPU 推理延迟在可接受范围。
3. **三分类派生**：θ 边界行为（|p_pos−p_neg| 恰好等于 θ 时归类正确）。
4. **方面级分析**：转折句切分（"画面很美但是剧情很烂"→画面正面、剧情负面）、锚点显式才报告、贝叶斯平滑在小样本下生效。
5. **L1 降级**：超时 3 秒返回本地结果、不卡死。
6. **评测框架**：指标计算正确性（Accuracy/F1/混淆矩阵/per-aspect P/R/F1/Cohen's κ）。

### 测试的先例

无（绿地项目，`docs/决策记录.md` 是唯一的既有文档）。测试风格按上面的"好测试"标准自建。

## Out of Scope

- **不训练/微调模型**（仅预留管线，见"预留训练管线"）。
- 不做智能问答/RAG。
- 不做推荐系统。
- 不做水军/垃圾评论检测。
- 不做星级评分预测。
- 不做情感时间趋势预测（只展示已有的时间分布）。
- 不做系统监控大屏、数据可视化大屏。
- 不做完整的社区功能（评论的社交互动、点赞、回复等）。
- 不做移动端 App 或小程序。
- 不做多语言支持（仅中文）。
- 不做 Elasticsearch / 全文检索引擎（MySQL 的 LIKE 查询对 4000 条数据够用）。
- 不做 Kubernetes 部署。

## Further Notes

1. **Q1 的一项决策需要确认**：是否接受"一次性 Python 导出 ONNX"（导出 `IDEA-CCNL/Erlangshen-Roberta-110M-Sentiment` → ONNX → int8）。这**不是训练**，只是格式转换，但需要装一次 Python 环境。研究已确认这是唯一合规方案（现成 ONNX 模型要么 27 下载、要么无许可证）。如果拒绝，则退化为纯规则 + LLM API，放弃本地深度模型，创新点 1 也就不存在了。**本 spec 假设接受（选项 a）**。强烈建议选 (c)：既然环境必须装，把 L3 训练脚本也一起写好（边际成本从 3–4 天降到约 1 天）。

2. **一个已知风险**：`transformers` 已升到 5.x，可能破坏 `optimum` 的 ONNX 导出。子代理正在核实。如果确实坏了，需要在 `ml/` 导出脚本里固定 `transformers` 到 4.x 版本。这不影响架构决策，只是安装时锁版本。

3. **方面级召回率会很低**，这是构造性缺陷（隐式方面如"太拖了"无法靠关键词捕获）。这是**预期行为**，不是 bug。论文里应如实报告低召回率，并把它作为"接受低召回、保住高精度"的设计选择来论证。

4. **答辩演示脚本**（5–8 分钟）：首页海报墙（30 秒）→ 电影详情页雷达图（2 分钟，主战场）→ 现场提交评论实时分析 + 切换三种模型（2 分钟，唯一交互冲击）→ 后台一键重跑 + 爬虫日志（1 分钟）→ 模型效果对比表（1 分钟）。**第 2、3 段必须零失误**，建议提前录备用视频。演示路径**绝不依赖实时网络请求**。

5. **8–10 周里程碑**：W1 环境+数据落库（最关键，先拿下数据）→ W2 L0 规则+评测框架 → W3 L2 ONNX → W4 方面级+关键词 → W5 后端 API+用户体系 → W6 前端 7 页 → W7 L1+异步+Redis → W8 实验+图表 → W9 论文初稿 → W10 论文修订+PPT+演示彩排+缓冲。**W10 是纯缓冲**，不要塞功能。
